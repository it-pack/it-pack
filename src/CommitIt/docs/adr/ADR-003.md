# ADR-003: RepositoryObserver as the RunIt-Integration Boundary

- Status: Accepted
- Date: 2026-08-22
- Deciders: CommitIt maintainers

## Context

CommitIt must be *execution-model ready* but **not** execution-model dependent.
It must open the door for a future `it-pack/commit-it-runit` adapter to map
operations to RunIt activities/occurrences, without CommitIt itself depending on
RunIt.

## Decision

Instrumentation is provided through a single narrow port, `RepositoryObserver`,
with three lifecycle hooks:

- `onStart(string $operation, array $context)`
- `onSuccess(string $operation, array $context)`
- `onFailure(string $operation, \Throwable $error, array $context)`

The port is applied via the non-intrusive `ObservedRepository` decorator, composed
in `RepositoryOpener`. The core `Repository` and the git adapter never depend on
any observer or on RunIt. CommitIt ships **zero** RunIt code.

The observer vocabulary (`operation` name + structured `context`) is designed to
map cleanly onto RunIt's Activity/Observation/Occurrence triad, but the mapping
lives entirely in the future RunIt adapter.

## Consequences

- Positive: CommitIt stays independently installable and RunIt-free.
- Positive: observation can be added/removed without changing call sites (decorator).
- Positive: a failed operation is still reported to `onFailure`, preserving the
  original `Throwable`; observer failures are routed to a separate, non-recursive
  path so observation never triggers further observed operations.
- Negative: richer RunIt semantics require a separate package, not changes here.
