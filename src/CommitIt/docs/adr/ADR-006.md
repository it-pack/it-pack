# ADR-006: Split the `Repository` Port into Focused Ports

- Status: Accepted
- Date: 2026-08-22
- Deciders: CommitIt maintainers

## Context

`src/Contract/Repository.php` bundled ~25 methods into a single god-port. This
violated the "keep interfaces small and focused" rule in `AGENTS.md` and made safe
extension impossible: adding an operation (e.g. `stash()`) required appending to
`Repository`, breaking every third-party implementation — exactly the
backward-compat trap `AGENTS.md` warns about.

## Decision

Split `Repository` into focused ports by capability:

- `CommitPort` — staging, commits, commit reads, `getPath`, `hasChanges`, `execute`.
- `BranchPort` — branch create/checkout/delete/list.
- `TagPort` — tag create/delete/list.
- `RemotePort` — remote add/remove/list and fetch/pull/push.

`Repository` becomes a convenience **union** interface:

```php
interface Repository extends CommitPort, BranchPort, TagPort, RemotePort {
    public function getWorkingTree(): WorkingTree;
}
```

New capabilities arrive as new ports added to the union, not as edits to a shared
interface. `GitPhpRepository` and `ObservedRepository` continue to `implements
Repository`; because `Repository` extends the sub-ports, they implicitly satisfy
each.

The `WorkingTree` port is **deliberately not** flattened into the union. A
repository *owns* a working tree (reached via `getWorkingTree()`); it is not itself
a working-tree operator. Flattening would force every `Repository` implementation to
also implement `listWorktrees`/`add`/`remove` and conflict with the `ObservedWorkingTree`
decorator (F2). `WorkingTree` therefore remains a composed collaborator.

## Consequences

- Positive: new operations are additive (new port composed in), never breaking to
  existing `Repository` implementers until they opt into the new port.
- Positive: consumers can depend on a narrow port (e.g. `BranchPort`) instead of the
  whole surface.
- Negative: this is a public-contract change; it ships before `1.0.0`
  (see `docs/REFACTORING_PLAN.md` F1).
- Negative: a third-party `Repository` implementation must now satisfy all four
  sub-ports. Because `Repository` extends them, a class `implements Repository` is
  already required to implement every method, so no additional work is imposed on
  existing implementers.
