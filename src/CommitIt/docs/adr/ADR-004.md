# ADR-004: Worktree Strategy (Composition over czproject Subclassing)

- Status: Accepted
- Date: 2026-08-22
- Deciders: CommitIt maintainers

## Context

CommitIt differentiates with linked git worktree support (`git worktree add/list/
remove`). `czproject/git-php` exposes an `execute()` passthrough on its
`GitRepository`, but subclassing `czproject` classes to add features is fragile
and couples CommitIt to the third-party class hierarchy.

## Decision

Implement worktrees through a **separate `GitPhpWorkingTree` value/service class**
that composes a `GitPhpRepository` and issues worktree commands via the
repository's `execute()` passthrough — **not** by extending `czproject` classes.

The `WorkingTree` port (`add`, `list`, `remove`) is the vendor-neutral surface;
`GitPhpWorkingTree` is the git adapter's implementation. Worktree paths are
validated and must not escape the repository's parent scope without explicit,
validated intent, and adding/removing a worktree must not corrupt the primary
checkout.

## Consequences

- Positive: the worktree logic is isolated in its own focused class and the
  `czproject` surface stays confined to `src/Adapter/Git/`.
- Positive: `GitPhpWorkingTree` is independently testable through the
  `MemoryRunner` and real-git functional suites.
- Negative: worktree support is git-specific; the `WorkingTree` port is only
  populated by the git adapter in 1.0.0.
