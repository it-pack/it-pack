# ADR-007: Exception Taxonomy — Validation vs VCS Operation

- Status: Accepted
- Date: 2026-08-22
- Deciders: CommitIt maintainers

## Context

The exception taxonomy conflated two distinct failure families. Validation
exceptions (`InvalidReferenceNameException`, `InvalidCommitMessageException`) are
thrown **before** any backend is contacted, when a caller supplies an invalid
branch/tag/commit-message. They are `LogicException`s. Yet their contract markers
extended `VcsOperationException`, a `RuntimeException` marker reserved for failures
that originate **from** a VCS backend.

Consequences of the conflation:
- `catch (VcsOperationException $e)` unexpectedly caught pre-backend validation
  errors (logic errors a caller should fix, not runtime/backend failures).
- `catch (RuntimeException $e)` did **not** catch them, contradicting the marker.

`GitExceptionMap` also reused the validation exception class for backend
"unknown revision"-style failures, muddying the two families further.

## Decision

1. Introduce `ItPack\CommitIt\Contract\Exception\ValidationException`, a marker that
   extends `CommitItException` directly (parallel to, not under, `VcsOperationException`).
2. Repoint `InvalidReferenceNameException` and `InvalidCommitMessageException`
   markers to extend `ValidationException`.
3. The concrete validation exceptions keep extending `\InvalidArgumentException`
   (logic errors) and now implement their `ValidationException`-based markers.
4. `GitExceptionMap` no longer emits validation exceptions for backend failures.
   Backend "invalid reference"-shaped errors now map to `VcsOperationException`, so
   the validation family is exclusively pre-backend.

## Consequences

- Positive: `catch (VcsOperationException $e)` only catches genuine backend/runtime
  failures; `catch (ValidationException $e)` cleanly separates input-validation
  failures. The marker hierarchy now matches the class hierarchy.
- Positive: the `ValidationException` family is reserved for pre-backend input
  checks, making the contract self-documenting.
- Negative: backend "unknown revision" errors are no longer the same type as
  boundary validation errors. This is intended — they are different failure modes;
  the message still carries the cause.
- Negative: this is a public-contract change; it ships before `1.0.0` (see
  `docs/REFACTORING_PLAN.md` F5).
