# ADR-002: Vendor-Neutral Vocabulary vs. Git-First Implementation

- Status: Accepted
- Date: 2026-08-22
- Deciders: CommitIt maintainers

## Context

The 1.0.0 scope is git only, but the public surface must not leak git slang
(`repo wrapper`, `worktree`, `hash`, `ref`) where a VCS-agnostic concept exists.
We must balance avoiding speculative abstraction against drawing a clean port
boundary.

## Decision

Express the public contract in **VCS-neutral terms**: `Repository`, `WorkingTree`,
`Branch`, `Tag`, `Remote`, `Commit`, `CommitId`, `CommitMessage`, `RepositoryPath`.

Git-specific mechanics (git invocations, ref-format rules, worktree plumbing) are
kept *inside* `src/Adapter/Git/`. The one deliberate, documented exception is the
generic `Repository::execute(string $command, array $args): string` escape hatch:
it is part of the `Repository` port but is explicitly documented as git-specific
and non-portable. Adapters for other VCS must decide their own escape-hatch
semantics.

## Consequences

- Positive: consumers write code against stable VCS concepts, not git internals.
- Positive: an alternative backend can be added without renaming public types.
- Negative: `execute()` is not meaningfully portable; it is a pragmatic bridge for
  git-only power users and is clearly flagged as such in documentation and
  contract PHPDoc.
