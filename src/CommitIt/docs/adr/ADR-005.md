# ADR-005: Value-Object Validation Rules

- Status: Accepted
- Date: 2026-08-22
- Deciders: CommitIt maintainers

## Context

Repository paths, reference names (branches/tags/remotes), and commit messages
are user-supplied and therefore potential injection or data-exfiltration vectors.
We need deterministic, pure validation applied **before** any value reaches the
backend, expressed as dedicated, immutable value objects.

## Decision

All validated concepts are dedicated value objects constructed through named
constructors (`RepositoryPath::from()`, `BranchName::from()`, etc.) that run a
pure validator. Two validators encode the rules:

### RefNameValidator (branches, tags, remotes)

Rules follow git's `check_ref_format`:

- Must not be empty; no leading/trailing whitespace.
- No control characters (`\x00-\x1f`, `\x7f`) or whitespace.
- No forbidden characters: `~ ^ : ? * [ \`.
- No `@{` sequence; must not be exactly `@`.
- No `..` (ambiguous range).
- Must not start or end with `/`, and must not contain `//`.
- No path component may start with `.` or end with `.lock`.

Invalid names throw `InvalidReferenceNameException` tagged with the ref kind
(`RefKind`: branch, tag, remote). Shell metacharacters such as `$(…)` or backticks
are *legal* git ref characters and are not rejected here; they are safe because
the git adapter passes arguments as an argv vector (no shell), so they are never
interpreted by a shell.

### CommitMessageValidator

- Subject must be non-empty after trimming.
- Subject must be a single line (no embedded newline).
- Subject length is bounded by `MAX_SUBJECT_LENGTH = 72`.
- Body is optional; when provided it must be non-empty after trimming.

Invalid messages throw `InvalidCommitMessageException`.

### Path scope

`RepositoryPath` is resolved and validated so stage/remove targets never escape
the repository root, and worktree paths never escape the repository's parent
scope without explicit, validated intent.

## Consequences

- Positive: injection-shaped inputs are rejected at the boundary, not at the
  backend; tests can fuzz ref names deterministically.
- Positive: commit-message size is bounded before reaching git, preventing
  unbounded buffers.
- Negative: the rules mirror git's `check_ref_format`, so a future non-git backend
  with different naming rules would need its own validator (the port stays
  neutral; only the git adapter supplies these rules).
